אין צורך במשתנים ב־`.env.local` או ב־Vercel: המשלוח מוגדר כולו בצד Supabase.

**אומת ב־24.10.2026:** המשתמש ביקש קוד ב־`/login` לחשבון המ״פ, בחלון פרטי. ב־auth logs: `POST /otp` החזיר 200 ב־11:00:18Z בלי קריאה ל־hook, אחריו `POST /verify` עם 200 ו־`login_method: otp` ב־11:00:36Z. המייל הגיע והכניסה הצליחה. לשם השוואה, ב־09:23Z, כשה־hook עוד היה פעיל, בקשת OTP נכשלה עם `Unexpected status code returned from hook: 500`.

**Site URL** ב־Authentication ← URL Configuration הוא עדיין `http://localhost:3000`, ו־Redirect URLs הם `localhost:3000/3001/auth/callback`. זה לא משפיע על הכניסה, כי התבניות שולחות קוד ולא קישור. אם יתווסף בעתיד מייל שמכיל קישור, צריך קודם להחליף את Site URL לכתובת הייצור.

### חזרה למצב הקודם

- **המיילים לא מגיעים:** בדקו ב־Authentication ← Logs. שגיאה `535` פירושה שסיסמת האפליקציה שגויה או בוטלה: צרו סיסמה חדשה ב־`myaccount.google.com/apppasswords` והזינו אותה ב־SMTP Settings.
- **חזרה מיידית למשלוח הקודם:** הפעילו מחדש את Send Email Hook ב־Auth Hooks. כשה־hook פעיל, Supabase שולח דרכו ולא דרך ה־SMTP. שימו לב: Resend עדיין ללא דומיין מאומת.
- **סיסמת האפליקציה נחשפה:** בטלו אותה ב־Google וצרו חדשה.

### מגבלות ידועות

- `barnash79@gmail.com` משמש גם כמייל הכניסה של פרופיל מ״מ 1 (בדיקה). כשיגיע המייל האמיתי של מ״מ 1, מעדכנים את המייל על אותו פרופיל. כתובת השולח לא משתנה.
- Gmail הוא שירות אישי ולא שירות משלוח טרנזקציוני. מיילים עלולים להגיע לספאם או ללשונית קידומי מכירות, במיוחד בהתחלה. כשיהיה דומיין, כדאי לעבור לספק טרנזקציוני (Resend עם דומיין מאומת).

## הוספת בעל תפקיד קיים (מ״מ 2–4, סמ״פ, מש״ד, רס״פ, חובש)

ב־`public.users` כבר קיימים פרופילים פעילים ומאושרים שעדיין לא קושרו לכניסה (`auth_user_id` ריק). אין ליצור להם פרופיל נוסף.

1. מאתרים את הפרופיל הקיים לפי תפקיד ויחידה (למשל מ״מ 2 / מחלקה 2) ורושמים את ה־`id`.
2. מעדכנים את `email` על **אותה שורה** לכתובת האמיתית, באותיות קטנות.
3. בעל התפקיד נכנס ל־`/login`, בוחר "קוד למייל", מזין את הקוד, ו־`claim_own_profile` מקשר את ה־Auth user לשורה. ההתאמה היא לפי מייל מאומת.
4. מאחר שהפרופיל כבר `active`/`approved`, הגישה נפתחת מיד לפי התפקיד והיחידה. מאמתים בדפדפן נפרד שהוא רואה רק את המסגרת שלו.

**פער ידוע (24.10.2026):** ב־`/admin` אי אפשר לשנות מייל של פרופיל קיים. אפשר לערוך רק תפקיד, יחידה, יחידה בפיקוד ורמה. "הזמנת משתמש" יוצרת תמיד שורה חדשה (`insert`) בסטטוס `pending`, ולכן הזמנת בעל תפקיד קיים דרך `/admin` תיצור פרופיל כפול. לכן שלב 2 מתבצע כרגע ב־Table Editor או ב־SQL ידני, כל שורה באישור מפורש. החלופה היא שינוי קוד שיאפשר עריכת מייל לפרופיל שעוד לא קושר (`auth_user_id is null`) ב־`/admin`, עם מבחן ממוקד.

## הוספת משתמש חדש לגמרי

אם אין פרופיל קיים לתפקיד: מ״פ או סמ״פ פותחים `/admin` ← הזמנת משתמש, עם שם, מייל, תפקיד ויחידה. המשתמש נכנס ב־OTP, `claim_own_profile` מקשר אותו, ואחרי זה מ״פ או סמ״פ מאשרים אותו ב־`/admin`. אישור נחסם בלי תפקיד ו־`unit_id` תקינים.

## כניסה בסיסמה

`/login` תומך גם בסיסמה (PR #15), אבל רק ל־Auth user שכבר מקושר לפרופיל. אין באתר הרשמה, שינוי סיסמה או איפוס. אין ליצור סיסמאות למפקדים אמיתיים או לתת גישת Auth ידנית בלי אישור מפורש לכל חשבון.

## אסור

- ליצור פרופילים כפולים לבעל תפקיד קיים.
- למחוק את הזמנות ההמתנה (שורות לא מקושרות) בלי אישור מפורש. זו פעולה הרסנית בנתוני אמת.
- להדפיס או להעתיק את סיסמת ה־SMTP או מפתחות למסמכים, לקוד או לצ׳אט.
